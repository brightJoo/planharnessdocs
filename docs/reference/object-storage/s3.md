# Reference — Object Storage (S3)

> **Consumer → Object Storage 경로가 전체 플랫폼 처리량의 상한을 결정**한다. 수집 트래픽이 크고 장기 보존이 필요하므로, 설계 전체가 **"대역폭을 가장 아끼는 방향"** 으로 기울어야 한다. 이 문서는 S3(또는 S3 호환 스토리지)를 쓸 때의 포맷·업로드·읽기·라이프사이클 원칙을 정의한다.

---

## 1. 이 프로젝트에서 S3의 위치

- **쓰기 주체**: Consumer 서비스. Kafka 배치를 누적 → **`.ndjson.gz` 한 오브젝트**로 업로드.
- **읽기 주체**: 리플레이 엔진(재생 시 원본 트래픽 조회), AI 분석 리포트, ad-hoc 분석.
- **Immutable 원칙**: 한 번 쓴 오브젝트는 **덮어쓰지 않는다.** 수정이 필요하면 새 객체로 다시 쓰고 이전 버전은 라이프사이클이 처리.

---

## 2. 설계 철학

| # | 원칙 | 의미 |
|---|---|---|
| 1 | **Bandwidth first** | 대역폭이 가장 비싼 자원. CPU(압축)·지연을 내주고 바이트를 줄인다. |
| 2 | **Streaming, never buffer** | RAM에 전체 배치를 담지 않는다. 읽기·쓰기 모두 chunk 스트리밍. 대형 배치에서 OOM 방지. |
| 3 | **Compress-on-write (gzip)** | Kafka 구간의 `zstd`는 transit 전용. Consumer가 **역직렬화 후 gzip으로 재압축** 해서 S3에 저장. 저장 시간·스토리지·downstream 읽기 대역폭 모두 절감. |
| 4 | **Line-delimited format (NDJSON)** | 한 줄 = 한 레코드. gzip과 궁합 좋음 + 부분 읽기·재시작 가능. |
| 5 | **Partition for locality** | 경로가 시간·서비스로 파티셔닝되어 있어 리플레이/분석이 **LIST 한 번 + prefix** 로 원하는 구간에 도달. |
| 6 | **Immutable objects** | 덮어쓰기 없음. 동일 prefix에 새 객체. 버전 혼선·동시성 문제 소거. |
| 7 | **Observable throughput** | 초당 업로드 바이트/건수·압축률·multipart 실패를 항상 관측. 대역폭이 주 자원이라 눈을 뗄 수 없다. |

## 3. 오브젝트 포맷 — `.ndjson.gz`

```
content                     filename                                content-type       content-encoding
────────────────────────────────────────────────────────────────────────────────────────────────────────
NDJSON 레코드 N건 → gzip → <batch-id>.ndjson.gz                   application/x-ndjson  gzip
```

**NDJSON(Newline-Delimited JSON)을 쓰는 이유**
- gzip과 함께 **순차 디코딩 가능** — 전체 파일을 메모리에 올리지 않고 한 줄씩 처리.
- 중간 손상 시 **해당 라인만 버리고** 이후 라인 계속 처리 가능 (일반 JSON은 전체 실패).
- `jq`, `aws s3 cp | zcat | grep` 등 표준 유닉스 파이프와 궁합.

**gzip을 쓰는 이유 (zstd·brotli 대신)**
- **호환성** — 어떤 S3 클라이언트·분석 툴이든 디코드 가능. `Content-Encoding: gzip` 표준 HTTP 지원.
- HTTP 트래픽은 반복 구조가 많아 **gzip만으로도 70-90% 압축** 달성. 더 공격적인 알고리즘 필요성 낮음.
- Kafka 구간은 `zstd`, 저장 구간은 `gzip` — 역할 분리(transit vs at-rest).

## 4. 경로 규약 (파티셔닝)

```
<env>/<service>/dt=<yyyy-mm-dd>/hour=<hh>/<batch-id>.ndjson.gz
```

| 세그먼트 | 값 | 이유 |
|---|---|---|
| `<env>` | `mvp` / `staging` / `prod` | 환경 격리. Cross-env LIST/GET 실수 차단. |
| `<service>` | `service-a` / `service-b` / `service-c` | 대상 서비스별 격리. 리플레이는 한 서비스에 집중. |
| `dt=<yyyy-mm-dd>` | 일자 | Hive-style 파티션 — 분석 툴(Athena 등) 호환. |
| `hour=<hh>` | 00~23 | 시간 단위 서브파티션 — 24배 압축 재생(K-3)과 맞물림. |
| `<batch-id>` | **ULID** | 시간 순서로 정렬 + 충돌 방지. UUID와 달리 prefix만으로도 시간 국소성. |

**LIST 비용 주의.** S3 LIST는 prefix 당 수수료·지연이 있다. **읽는 쪽은 반드시 prefix를 좁혀서** 호출 (예: `mvp/service-a/dt=2026-04-19/hour=14/`).

## 5. 업로드 전략 — Streaming Multipart + gzip

```
[Kafka records] → [NDJSON encoder] → [gzip encoder] → [multipart buffer, 16 MiB] → [S3 UploadPart]
       ↑ stream        ↑ line-by-line    ↑ 스트리밍 압축       ↑ 한 part 차면 업로드, 병렬 N개
```

| 항목 | 값 | 비고 |
|---|---|---|
| Multipart threshold | **8 MiB** 초과 시 multipart 사용 | boto3 `TransferConfig.multipart_threshold` |
| Part size | **16 MiB** (하한 5 MiB, 상한 5 GiB) | 네트워크 상황 따라 32–64 MiB로 상향 가능 |
| 최대 part 수 | **10,000** (S3 제약) | 초과 시 단일 오브젝트로 담을 수 없음 — 배치 분할 |
| 동시 part 업로드 | **10 concurrent** (boto3 기본) | 더 넓히면 대역폭↑ but RAM·연결수↑ |
| 재시도 | 각 part 독립 재시도 | 전체 재업로드 불필요 |
| 체크섬 | `x-amz-checksum-crc32c` 권장 | 무결성 확인, part 단위 재시도에도 일관 |

**스트리밍 압축이 핵심.** "전체 배치를 gzip으로 다 압축한 뒤 업로드"가 아니라 **gzip encoder의 output이 multipart 버퍼로 흘러들어가고, 버퍼가 part size 도달하는 순간 업로드 개시**. 이래야 메모리 사용이 `part_size × concurrency` (예: 16 MiB × 10 = 160 MiB)로 **상수**로 유지된다.

**미완료 multipart 정리 필수.** `AbortIncompleteMultipartUpload` 라이프사이클 규칙(예: 1일)을 반드시 건다. 방치 시 **숨은 스토리지 비용**으로 누적.

## 6. Compression 정책

| 항목 | 값 | 이유 |
|---|---|---|
| Algorithm | **gzip** | §3의 호환성·HTTP 표준 이유 |
| Level | **6** (기본값, 균형) | 1은 빠르지만 압축률↓, 9는 CPU·지연 폭증하면서 이득 미미 |
| Window size | gzip 기본 | 튜닝 불필요 |
| 적용 레이어 | **Consumer 프로세스** | Object Storage가 아닌 쓰기 클라이언트 책임 |

**CPU 영향.** Consumer는 대상 서비스 Pod와 분리돼 있어 **compression CPU가 host 서비스에 영향 주지 않는다.** 따라서 level을 낮출 이유 제한적. 다만 consumer 자체 CPU 포화 시 level 3~4로 내려 throughput 확보 가능.

## 7. 읽기 (리플레이·분석)

| 경로 | 전략 |
|---|---|
| **전체 읽기** (리플레이 엔진) | `GET` → streaming gunzip → NDJSON line-by-line 처리. 전체 버퍼 금지. |
| **부분 읽기** (ad-hoc, 앞부분만) | `GET` with `Range: bytes=0-N`. gzip 스트림 앞부분만 디코드 가능. |
| **파티션 발견** | `LIST` with tight prefix (§4) → 결과 페이지네이션 준수. |
| **대량 읽기** (리플레이 동시 파싱) | 여러 오브젝트 **병렬 `GET`** — S3는 파티션 당 높은 read RPS 허용. |

**Range 요청은 gzip 파일에서도 유효** — gzip stream은 start부터 순차 디코드만 가능하므로 "오브젝트의 앞 N 바이트"를 범위 요청하면 앞부분 레코드를 얻는다. 뒷부분만 떼서 읽으려면 gzip concatenation을 쓰는 고급 전략이 필요(이 프로젝트 범위 밖).

## 8. 라이프사이클 (Lifecycle)

| 경과 시간 | 전환 | 이유 |
|---|---|---|
| 즉시 | Standard | hot path. 리플레이가 최근 데이터 자주 참조. |
| N일 | Standard-IA | 조회 빈도 낮아지는 시점. 저장 단가↓ |
| M일 | Glacier Instant/Flexible | 장기 보존·감사 목적 |
| L일 | **Expire(삭제)** | PII 보존 요건 + 저장 비용 상한 |
| **동시 정책** | `AbortIncompleteMultipartUpload` (1일) | §5 미완료 multipart 청소 |

N/M/L 구체값은 운영 비용·보존 요건과 함께 튜닝.

## 9. 필수 메트릭

| 메트릭 | 의미 |
|---|---|
| `s3_upload_bytes_total` | 업로드 누적 바이트 (전-압축/후-압축 분리) |
| `s3_upload_duration_seconds` (p50, p95) | 오브젝트당 업로드 지연 |
| `s3_multipart_initiated_total` / `_completed_total` / `_aborted_total` | multipart 수명 추적. aborted가 쌓이면 orphan 의심 |
| `s3_put_error_rate` | 5xx·429 비율 — 재시도·backoff 튜닝 신호 |
| `gzip_compression_ratio` | `(raw_bytes / compressed_bytes)` — 70-90% 정상, 갑자기 떨어지면 데이터 포맷 변질 의심 |
| `s3_active_multipart_uploads` | 미완료 상태의 현재 multipart 수 — 라이프사이클 청소와 교차검증 |
| `s3_list_rps` / `s3_get_rps` | 읽기 쪽 프로파일 |

## 10. 금지 / 주의

- ❌ **배치 전체를 RAM 버퍼링 후 업로드** — 대형 배치 OOM의 전형적 경로
- ❌ **`.json` (단일 JSON 배열) + gzip** — streaming decode 불가. 반드시 NDJSON
- ❌ **미완료 multipart 청소 라이프사이클 누락** — 숨은 비용 폭증
- ❌ **오브젝트 덮어쓰기** — Immutable 원칙 위반, 버전 혼선
- ❌ **공개 ACL / 버킷 정책** — 마스킹 전 원본이라도 외부 접근 경로 만들지 않음
- ❌ **prefix 없는 LIST** — 전체 버킷 스캔 비용
- ❌ **Small-object 폭주** (수 KB 객체 수백만 개) — 메타데이터·LIST 비용 폭증. 배치로 뭉쳐 N MiB 단위로.

## 11. 원칙 위반 신호 (리뷰 체크리스트)

- [ ] Consumer 코드에서 `readAll()` / 전체 바이트 배열 로드 — streaming 원칙 위반
- [ ] Object 확장자 `.json` / `.json.gz` (단일 JSON) — NDJSON 원칙 위반
- [ ] Multipart 설정 없이 큰 배치 단일 `PUT` — 메모리·재시도 비용 폭증
- [ ] `AbortIncompleteMultipartUpload` 라이프사이클 규칙 부재
- [ ] `gzip_compression_ratio` 메트릭 미노출 — 저장 비용을 블랙박스로 운영하는 꼴
- [ ] 경로에 `<env>` 없음 — cross-env 사고 위험

- Max object size: 5 TiB
- Min multipart threshold: 구현체 권장 5~8 MiB 이상
