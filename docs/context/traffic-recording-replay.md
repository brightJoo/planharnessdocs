# Context — 운영 트래픽 레코딩 & 리플레이 플랫폼

> 이 문서는 **비즈니스/문제 컨텍스트**만 담는다. 기술 선택(저장소·브로커·부하 도구·캐시 등)은 여기 들어오지 않고 HLD/ADR에서 다룬다.
>
> *포트폴리오 공개를 위해 팀·조직·내부 시스템 명칭·실제 일정은 일반화했다. 규모·제약·의사결정 트레이드오프 등 설계 본질은 보존했다.*

---

## 1. 왜 필요한가 (Problem Statement)

운영(프로덕션) 트래픽을 기반으로 **부하·회귀 테스트를 재현 가능하게 수행**할 수단이 없다.

- 운영에서 실제로 발생하는 요청 패턴을 사전에 쌓아 두고 **필요 시점에 압축/증폭 재생**할 방법이 없음.
- 합성(synthetic) 부하 시나리오만으로는 실제 사용자 요청의 분포·조합을 재현하지 못함.
- 신규 기능 배포 / 아키텍처 변경 시 **"운영에서 정말 버티는가"** 에 대한 사전 검증 근거가 부족.
- 장애 사후분석과 용량 계획 의사결정에 쓸 **비정형 결과 리포트**가 부족 — 사람이 로그·지표를 일일이 붙여 보고 있다.

→ 운영 트래픽을 **일정 기간 수집 → 원하는 시점·배율로 재생 → 결과를 자동 요약**하는 플랫폼이 필요하다.

---

## 2. 사용자 / 스테이크홀더

### 2.1 이 플랫폼의 최종 사용자
| 역할 | 무엇을 하러 오는가 |
|---|---|
| 유저 서비스 개발자 | 자기 서비스의 배포/변경 전에 운영급 부하에서 버티는지 확인 |
| 테크리드 | 아키텍처 변경·언어/프레임워크 전환 의사결정 전 부하 영향 판단 |
| SRE | 용량 계획 / 장애 재현 / 병목 조사 |
| PM | 프로모션·캠페인 트래픽 규모 하에서의 서비스 건전성 사전 확인 |

### 2.2 이 플랫폼의 개발·운영 팀 (역할 기준)
| 역할 | 담당 범위 |
|---|---|
| Platform Lead | 전체 설계·의사결정 게이트·외부 조직 커뮤니케이션 |
| Collection Engineer | 수집 라이브러리 · Producer · 오브젝트 스토리지 적재 · On/Off API · PII 마스킹 코어 |
| Replay Engineer | 리플레이 엔진 · 분산 부하 러너 연동 · 매트릭 집계 · 대시보드 |
| Auth Integration Engineer | 리플레이 시 인증 토큰 확보·주입·치환 |
| UI Designer | Record/Replay 대시보드 시각 디자인 (파트타임 합류) |

### 2.3 승인·의존 관계에 있는 외부 조직
| 조직 | 관계 |
|---|---|
| 보안팀 | **마스킹 가이드 / 인증 토큰 취급 가이드** 공급. 가이드 산출물이 코어 모듈 일정을 지배. |
| 서비스 플랫폼팀 | 인프라 / 토큰 발급 / 결과 분석용 외부 연동 채널의 오너. |
| 인프라팀 | 공유 캐시·오브젝트 스토리지 등 공통 자원의 접근 권한. **전용 인프라 신규 할당은 타임라인상 불가** — 공통 자원에 얹는 방식으로 합의. |
| 파트너 도메인 팀 | 대상 서비스 3곳 중 한 곳. POC 기간에는 라이브 도입 보류, **POC 성공 후 켜달라고 요청**하는 순서. |

> **Open Question C-1 [부분 해소]**: 리플레이 결과의 주된 소비자 = 유저 서비스 개발자 + 테크리드 + SRE + PM. 단, "언제·어떤 의사결정에 쓰이는가"의 **정형화된 use-case 문서**는 아직 없음 — 다음 회의에서 성공 사례 2~3개 정의 필요.

## 3. 범위 (Scope)

### 3.1 이번 iteration(MVP / POC)에 포함
1. **수집 (Record)**
   - 대상 서비스: **Service A (콘텐츠성) / Service B (노출·디스플레이) / Service C (프로모션)** — 3개 도메인
   - 대상 요청: **퍼블릭 API** 만. 내부(internal) 요청은 퍼블릭 호출이 내려가면서 자연스럽게 동반되므로 별도 수집하지 않는다.
   - 포함 요청 유형:
     - 읽기(Read) 전반
     - 쓰기(Write) 중 **대표 시나리오 1건** (예: 보상/혜택 수령류) — 사이드이펙트(카운트 증가 등)를 안전하게 재생할 수 있는 대표 케이스로 선정
   - 운영 모델: **선별 기간 On/Off** — 365일 상시 수집은 금지.
2. **재생 (Replay)**
   - 서비스별 리플레이 실행
   - **실행 파라미터**: 날짜 범위, 시간 압축(압축 배율), RPS 지정
   - 서비스 단위 + API 단위 **블랙/화이트 리스트**
   - 실행 전 **사전 미리보기(예상 RPS, 동작 예정 API 목록, 사전 통계)**
   - **증폭 배율** — 운영 트래픽을 실제보다 확대해서 재생해야 병목이 드러남. 현재 한계치 언급: **약 1,000배 증폭이 필요**한 수준.
3. **가시성 (Observability)**
   - 레코딩 상태 대시보드 (적재 카운트, 서비스별 상태, 용량)
   - 리플레이 실행 매트릭 (**서비스별 · API별 RPS 추이 · 상태코드 분포**)
   - **그래프 중심 UI** — 원시 로그 나열형 불가.
4. **결과 분석**
   - 리플레이 결과(비정형 데이터) → **AI 기반 리포트** (문제 서비스 자동 식별)
   - Slack 알림은 "있으면 좋음" 수준
5. **운영 제어**
   - **서비스 등록(서비스명 ↔ 호스트 매핑)** 자동화: 라이브러리가 최초 폴링 시 자동 등록 → 사람 수기 등록 폐지
   - 특정 API(예: 헬스체크 `actuator/health`) 기본 제외
   - On/Off:
     - 즉시 실행
     - 날짜 윈도우 예약 실행 (예: `D-day 11시 ~ D+1 11시`)
6. **인증 처리**
   - 리플레이 시 실제 인증이 통과되도록 **로그인 사용자 토큰을 헤더에 주입**
   - 토큰 확보 경로 미확정 (C-9 참고)

### 3.2 이번 iteration에서 명시적으로 제외
- **대표 시나리오 외의 쓰기 트래픽**(주문·결제 등)
- **내부 마이크로서비스 간 호출의 독립 수집**
- **자동 중단 / 세이프티(부하 과다 시 자동 차단) 기능** — 사이클 1회 돌린 후에 추가 개발
- **별도 FE 모듈** — API + 최소 대시보드만 제공 (SSO 경유)
- **파트너 도메인 팀 서비스의 라이브 연동** — POC 기간에는 off, 검증 후 on 요청
- **자체 전용 인프라 구축** — 공통 자원에 얹기
- **QA / PR 정식 절차** — 시간 부족으로 직접 main 커밋 + 개발자 자체 테스트. **이후 iteration에서 복원 필요.**

> **Open Question C-2 [부분 해소]**: 대표 쓰기 시나리오를 1차 범위에 넣은 근거 — **쓰기 사이드이펙트(예: 카운트 증가 같은 부수 효과)** 를 안전하게 다룰 수 있는 대표 케이스로 선택. 이 판단 근거를 비즈니스 오너가 한 줄로 확정 필요.

## 4. 제약 (Constraints)

### 4.1 운영 안정성
- 수집 훅을 붙인 대상 서비스의 **메모리/CPU/지연 증가가 "유의미하지 않은" 수준**이어야 도입 가능.
  - "유의미하지 않음"의 **정량 기준은 동일 RPS 조건에서 라이브러리 OFF vs ON 메모리 사용률 차이(%)**로 측정한다. — K-1 참고.
- 수집 **Off 구간에는 네트워크/컴퓨팅 비용 0** — 네트워크 호출 자체가 발생하지 않아야 한다.
- **폴링 설계 주의**: 전체 Pod **수천 대 규모** 환경에서 폴링 빈도가 높아지면 동시 요청 RPS가 급증할 수 있다.

### 4.2 개인정보 / 민감정보
- **최종 상태**: 수집·저장된 트래픽에 **개인정보가 포함되어서는 안 된다.**
- **1차 MVP (레코딩·리플레이 사이클을 처음 돌리는 단계)에서는 마스킹 스킵 허용**.
- **코어 모듈 단계(1차 사이클 이후)** 에서 PII 마스킹·사용자 식별 정보 치환 등을 정식 구현. 이 작업의 선행 조건은 **보안팀 가이드 수령**.
- 만료되는 세션 쿠키는 재생 시 자연 무효화되므로 별도 처리 부담 없음.
- 인증 헤더/쿠키(`Authorization`, `Cookie`)는 **수집 자체는 수행** — 리플레이 시 유효 토큰으로 치환·주입 필요.

### 4.3 인증 토큰
- 리플레이 요청이 **401로만 반환되면 서버가 죽지 않아** 본래의 부하 테스트 목적을 달성하지 못한다.
- **토큰 확보 경로 2안** (둘 중 어느 쪽이 될지는 C-9 참고):
  - (a) 서비스 플랫폼팀에서 **비프로덕션 환경 토큰** 공식 발급
  - (b) 개발 참여자 **개인 계정 N명의 토큰**만 받아 제한 운용
- 보안팀 가이드가 병목 — **가이드 전에는 코어 모듈 작업 보류**.

### 4.4 팀·일정
- **참여 인력**: 엔지니어 3명(Collection · Replay · Auth) + 디자이너 1명(파트타임)
- **타임라인 (상대 표기)**:
  - **Week 1 진입 전**: Collection Engineer의 선행 업무 마감 → 본 프로젝트 합류
  - **Week 1 주초**: 1차 테스트 — 주초 오전까지가 기본 마감, 최악의 경우 오후까지 허용 / 익일 이월 ❌
  - **Week 2**: 리드가 **ETA + ADR 정리 + 분석 과정 재검토** 일괄 수행
- 일정상 완벽한 1차 구현보다 **"작동하는 최소 구성 → 개선"** 을 최우선한다.

### 4.5 조직·리소스 환경
- **전용 인프라 신규 할당 금지**에 가까운 환경:
  - 전용 RDB 신규 구축은 IaC 기반 인프라 설정이 선행되어야 하므로 이번 사이클에는 **불가** → 로컬 메모리 또는 기존 공유 RDB의 커먼 스키마 사용으로 우회.
  - 전용 캐시 인프라 신규 할당 불가 → 공유 캐시에 얹기. 용도는 큐잉·매트릭 캐싱 수준의 가벼운 사용.
- **공통 자원에 얹는 방식**이 기본 원칙. 실패 시 로컬 메모리.

### 4.6 커뮤니케이션·작업 규율
- 이 업무에 관한 보고/싱크는 **ASAP** 원칙 — "완벽해질 때"가 아니라 "근거가 생겼을 때" 공유한다.
- **리드를 경유하는 커뮤니케이션**: 구현자 간 직접 설계 논의 전에 **리드에게 옵션을 정리해서 먼저 보고**하고 정렬한다.
- **완료 공유 방식**: PR 없이 main 직접 커밋 후 리드에게 맨션 — "됐다"만 남긴다. (이번 MVP 한정)

### 4.7 외부 도구 / 도입 가능성
- **분산 부하 러너의 오퍼레이터형 도입은 이번 사이클에서 불가** — 도입 경험 부재 + 공용 오브젝트 스토리지 연동 이슈 + 외부 팀 의존성 제거 원칙. → 내장형 러너로 우선 진행, 향후 iteration에서 오퍼레이터형 도입 여지 남김.

### 4.8 ⚠️ 즉시 결정 필요한 기술적 스코프
이 항목들은 **technical decision으로 ADR에서 결정**되지만, 현재 타임라인상 블로커이므로 오너·결정 기한을 여기서 한 번 더 고지한다:

| 블로커 | 오너 | 결정 기한 |
|---|---|---|
| 저장소 선택 (로컬 메모리 / 공유 RDB 커먼 스키마 / 지연된 전용 RDB) | Replay Engineer | Week 1 주초 이전 |
| 토큰 확보 경로 (a vs b) | Platform Lead + Auth Integration Engineer | 보안팀 응답 수령 직후 |
| 증폭 리미트 해제 수준 (10x → 1,000x) | Replay Engineer | Week 1 주초 오전 |

## 5. 목표 / 성공 기준 (KPI & Success Criteria)

### 5.1 정량 KPI
- **K-1 (오버헤드)**: 동일 RPS 조건에서 **라이브러리 OFF 대비 ON 상태의 메모리 사용률 증가치(%)**가 "유의미하지 않음"으로 합의될 수 있는 범위여야 한다.
  - ⚠️ "유의미하지 않음"의 정확한 수치 임계(예: +X% 이내)는 **Validation 단계 진입 전에 확정** 필요. — Open Question C-4 유지.
- **K-2 (증폭 역량)**: 재생 시 **최소 1,000배 증폭**이 가능해야 한다. (현 프로토타입은 10배 제한 → 해제 필요.)
- **K-3 (압축 재생)**: 24시간 수집분을 **약 1시간 창**으로 압축 재생할 수 있다 (24배 시간 압축).
- **K-4 (범위 달성)**: Service A(콘텐츠성) / B(노출·디스플레이) / C(프로모션)의 **퍼블릭 읽기 + 대표 쓰기 시나리오**를 재생 시 재현한다.

### 5.2 정성 KPI
- **Q-1 (가시성)**: 레코딩 상태와 리플레이 결과가 **그래프 중심 대시보드**로 제공된다. 원시 로그 나열 불가.
- **Q-2 (자동화)**: 서비스 등록(서비스명↔호스트) 사람 수기 입력이 필요하지 않다 — 라이브러리 최초 폴링 시 자동.
- **Q-3 (결과 해석)**: 리플레이 결과 비정형 데이터에서 **문제 서비스를 사람 개입 없이 1차 식별**하는 AI 리포트가 제공된다.
- **Q-4 (향후 안전 장치)**: 자동 중단 세이프티는 MVP에 없으나, **사이클 1회 성공 직후** 바로 개발 대기열에 들어간다.

### 5.3 Validation 합격/불합격 판정 기준 (다음 단계 확정)
> **Open Question C-5 유지**: 리플레이 결과를 **어떤 지표로 합격/불합격 판정**할 것인가(에러율 기준, P99 지연 임계, 특정 엔드포인트 완수율 등) — Validation 문서 작성 전 반드시 확정.

## 6. 참고 — 사전에 검토된 외부 레퍼런스 (비즈니스 관점)

> 구현 방식 비교가 아니라, "다른 곳은 왜 그 방식을 쓰고, 그게 우리 환경에 맞는가"의 맥락만 기록.

- 시장에 **사이드카 기반으로 Ingress 트래픽을 수집하는 상용/오픈소스 제품**이 존재하나:
  - 샘플링을 기본 비율 이하로 낮추지 않으면 운영 Pod 수준의 네트워크 오버헤드가 커진다.
  - 저장소 선택·샘플링 디폴트 등이 우리 환경과 맞지 않는다.
- 대시보드 쪽은 **외부 시각화 솔루션 iframe 연동을 검토했으나 보안 경계를 열어야 해서 제외** — 자체 대시보드를 그리는 방향으로 전환.
- 결론: "기존 제품 그대로 도입" 경로가 아니라 **우리 제약(인프라 할당 불가, 외부 팀 의존성 최소화, PII 요구)에 맞춘 수집·재생 방식**을 자체 설계해야 한다.

## 7. 이 문서가 답하지 않는 것 (의도적으로)

다음은 기술 선택·설계 영역으로, `docs/hld/`, `docs/adr/`, `docs/lld/`에서 다룬다:

- 트래픽을 **어떻게** 수집할 것인가 (라이브러리 / 사이드카 / eBPF / Ingress mirror 등)
- 전송 매체 (브로커 · 배치·압축 전략)
- 저장소 (오브젝트 스토리지 경로/포맷/파티셔닝)
- 재생 엔진(내장형 vs 오퍼레이터형) 및 분산 VU 제어 메커니즘
- 매트릭 캐싱 전략 (TTL / refresh-ahead / multi-GET 합치기 등)
- 마스킹을 어느 레이어(Producer / Consumer / 재생 시점)에서 수행할지
- AI 리포트에 어떤 모델·파이프라인을 쓸 것인지
- 인증 토큰 주입·치환 방식(토큰 풀 vs 개인 토큰 위임)
